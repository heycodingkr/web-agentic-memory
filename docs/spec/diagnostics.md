# Diagnostic tracing and log storage

HTTP, remote MCP, CLI, stdio MCP, and browser errors share a 32-character opaque `x-wam-trace-id`. The server preserves a valid ID and replaces malformed IDs. Every observed response includes the reference, including auth/rate-limit failures. HTTP-200 JSON-RPC/tool failures are recorded for both JSON and finite SSE POST replies. The dispatcher supplies only closed operation/error metadata through an internal response extension; the observer does not collect the stream body. Tool failures expose the same request reference in `result._meta.trace_id`, while RPC parse/envelope failures expose it in `error.data.trace_id`. Idle SSE GETs retain connection status and header latency without waiting for EOF or inspecting payloads. CLI prints the reference to stderr; MCP keeps stdout JSON-RPC framing; web API errors carry the reference.

Production startup wraps the router with `diagnostics::observe`. `WAM_LOG_DATABASE_URL` selects a separate PostgreSQL log database; otherwise `WAM_DATABASE_URL` is used. Local development writes SQLite at `WAM_DIAGNOSTICS_PATH` or `WAM_DATA_DIR/diagnostics.sqlite`. The independent, idempotent schema in `crates/wam-server/src/diagnostics/schema.sql` creates `wam_diagnostic_events` and trace/error/retention indexes. Non-loopback PostgreSQL requires verified TLS. Connection values and driver errors are not emitted.

Stored data is closed metadata: event ID, trace ID, source, operation category, error category, HTTP status/method, elapsed milliseconds and server receipt time. Remote MCP recall input failures also carry an optional, allowlisted `error_reason`: `invalid_arguments`, `invalid_url`, `invalid_task_category`, `invalid_keywords`, `invalid_kind`, `invalid_limit`, `invalid_recall_query`, or `validation_rejected`. The server preserves it from argument parsing or service validation into `result._meta.error_reason`, the stored JSON document, and alert email; tool text provides fixed recovery guidance. Client diagnostic intake still rejects this additional field. Unknown reason values fail deserialization, and old documents without the field remain readable; their historical validation reason cannot be recovered. A microsecond timestamp orders events received in the same second; older records use their receipt second. Internal email checkpoints store only the last delivered event ID and ordering time and are never emailed as errors. Tokens, cookies, account/device IDs, argv/stdin, tool arguments, request/response bodies, actual URL/route/query values, user messages and raw stack traces are excluded. Client source/status are diagnostic claims, never authorization, score, or abuse-proof evidence.

Browser uncaught errors use a normalized page operation. SvelteKit 3 navigation hooks use the destination event route rather than the previous window location. Framework/app 4xx errors retain the framework's safe status/message and are recorded as ordinary `http_error` events, excluded from alert email; unknown runtime errors remain actionable even if they carry a 4xx status property. When the rejection reason came from a WAM API call, its safe trace ID, operation, and HTTP status are reused so the client event can be queried with the originating request. Error messages, stack frames, and page paths remain excluded.

CLI and stdio MCP reuse a valid response `x-wam-trace-id` for JSON, empty-body and recall failures; malformed response IDs fall back to the generated request ID. Local CLI input/auth/account failures and stdio I/O failures print their recorded reference to stderr, preserving MCP stdout framing. Device-link operations use the closed `device` category. MCP preserves API failure categories instead of relabelling server/network/contract failures as invalid tool input. A configuration error that prevents constructing a valid API endpoint cannot upload a diagnostic; it remains a local stderr error.

`POST /v1/telemetry/events` accepts one schema-v1 closed event, at most 2 KiB, with bounded IDs/status/duration. Extra fields and unknown enums fail without echoing the input. Event IDs deduplicate replay. The anonymous intake has an in-process 60/minute peer limit, bounded peer state, and does not trust forwarded IP headers. It is independent of the API's shared account/IP admission. No public log-reading route is exposed.

The writer runs on a dedicated thread with a 256-command channel and a bounded 512-event retry backlog. Enqueue never blocks a business response. Temporary write failures retry; closed PostgreSQL connections reconnect with timeouts. Oldest events can be dropped under sustained outage/overload; `Diagnostics::dropped_events()` exposes that count. This is bounded operational diagnostics, not a lossless financial journal. PostgreSQL statements/locks have timeouts. Graceful server shutdown flushes pending diagnostics.

Logs retain seven days and at most 100,000 rows after cleanup (cleanup every 64 queued writes and every minute). SQLite uses WAL so an operator's read transaction does not block diagnostic ingestion; files use owner-only permissions. External readers should set a bounded busy timeout. Client offline queues retain at most 100 closed events for seven days in private per-origin directories; a later successful request drains at most ten within a total 800 ms deadline. `WAM_TELEMETRY=off` disables CLI/MCP uploads and queue access. Browser uploads use a bounded in-memory queue, retain failed events while the tab stays open, and retry after a five-second cooldown on connectivity/API recovery; `localStorage['wam.telemetry.enabled']='false'` disables client capture independently from contribution consent. Necessary server request diagnostics still contain no account linkage.

Set `WAM_DIAGNOSTICS_EMAIL_TO` to enable operational email alerts. The server reuses `RESEND_API_KEY` and `WAM_EMAIL_FROM`; `WAM_EMAIL_IDENTITY_SECRET` is only needed for email login. A background worker sends at most one digest per minute, up to 50 events per email, and resumes from a stored checkpoint with a stable Resend idempotency key. On first enable it considers errors from the previous ten minutes. Routine HTTP 4xx responses are omitted to avoid mail from expected authentication, validation and missing-route responses. The email includes only source, operation, closed error code and optional reason, status, duration, timestamp and trace ID. It explicitly explains that HTTP status describes transport delivery, so an MCP tool can fail with HTTP 200. Absent validation reasons are displayed as `unknown`. It never includes request URLs, user messages, payloads or stack text. If mail delivery fails, the same batch is retried; telemetry ingestion and user responses continue independently.

Operator query, using a trace reference copied from an error:

```sql
SELECT received_at, source, operation, error_code, status_code, document
FROM wam_diagnostic_events
WHERE trace_id = '<32-character reference>'
ORDER BY received_at;
```

Verification: `crates/wam-server/tests/diagnostics.rs`, disposable-DB `postgres_diagnostics.rs`, client telemetry/spool tests, browser telemetry tests and [local smoke](../test/local-smoke.md). The smoke runs actual CLI/MCP binaries and an actual browser against an isolated fixture, then compares trace references with persisted SQLite rows. Synthetic OAuth/model/replay fixtures do not claim live external-provider acceptance.
