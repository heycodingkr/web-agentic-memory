# Google Calendar — Arise live workflow benchmark

최종 확인: 2026-10-31 · 이슈 #103 / #126 · **R8: 짧은 L1로 T·M 모두 통과, 이번 비교에서 M 시간·호출 감소**

## R8 — 실제 막힌 경로를 줄인 짧은 메모리

기본 Calendar 힌트 세 개의 L1 본문을 합계 1,852자에서 1,103자(40.4% 감소)로 줄였다. 제목·현지 시각·시간대를 미리 채운 미저장 편집기 진입, Custom 반복 요일의 중복 선택 방지, 변경하지 않을 회차는 편집기 대신 저장된 팝업으로 확인하는 지침을 남겼다. 이 계정의 미저장 probe에서는 `recur=RRULE:...BYDAY=MO...`가 화요일로 표시되어, 기본 지침은 반복 규칙을 UI에서 설정하도록 한다.

새 seed를 적재한 격리 로컬 WAM API에서 실제 recall한 **L1만** M에 제공했다. L2는 버전·본문 대조용으로 따로 조회했고 작업자에게 전달하지 않았다. 전체 작업 프롬프트는 T 1,271자, M 2,465자였다. 입력창 copyback과 실행기 원문 일치, 자동 과거 기억 두 주입의 부재, 두 조건의 동일한 시작 페이지 wrapper를 확인했다.

| 조건 | 전체 작업·독립 확인 | 실행 시간 | 외부 도구 경계 | 실행 중 관찰 |
|---|---|---:|---:|---|
| T — 작업만 | 통과 | 431.108초 | 114 | stale 참조 거부 1회 |
| M — 수정한 L1 | 통과 | 237.169초 | 68 | 시작 시 tab_busy 거부 1회 |

이번 한 쌍에서 M은 **193.939초(44.99%)**, 외부 도구 경계 **46회(40.35%)**가 적었다. 같은 설치 Arise 0.1.60, `gpt-6-luna/max`, 새 대화, 실행당 900초다. 순서는 M→T이며 양쪽의 작업·도구 규칙은 같다. 양쪽 모두 browser_script는 금지했고 functions.exec의 여러 허용 도구 묶기는 허용했다. 표는 실제 외부 호출 경계를 센다. 별도 AST 소스 감사의 개별 브라우저 도구 호출은 T 176회, M 98회다. 이 두 로그에는 해당 호출을 감싼 조건·반복·동적 간접 호출이나 스크립트 실행 오류가 없어, 묶음 수 차이와 별개로 개별 호출도 줄었음을 확인했다. 실행 중 추가 memory 호출과 감사에서 탐지한 eval 변경 패턴은 모두 0이었다.

독립 검증자는 각 조건의 정확한 QA 제목을 별도 탭에서 검색해 결과가 세 건뿐임을 확인하고 **세 회차 팝업을 각각 다시 열었다**. LA 11월 2·16일 09:00–09:30, 9일만 10:00–10:30이며 월요일 3회·Los Angeles가 표시됐다. GMT+9 화면의 11월 3·17일 02:00, 10일 03:00과 일치했고 네 번째 회차가 없었다. 두 QA 시리즈만 모든 일정 범위로 삭제한 뒤 새 탭 검색 0건을 확인했다. 독립 확인 중 popup 전환의 이전 내용 읽기와 정리 클릭 재시도는 작업 수치 밖이며 #27에 남겼다.

이번 비교는 R7 경로를 보고 수정한 개발 관찰이다. 별도 미사용 과제나 반복 통계가 없고 조건당 한 번이며 순서는 무작위가 아니고 로그인·캐시 상태를 공유한다. 힌트 본문과 L2 전달 방식을 함께 바꿨으므로 각 변경의 효과를 분리하지 못했다. 준비의 메모리 조회·독립 확인·정리 시간은 제외했다. **일반적인 속도·비용 절감이나 자동 Arise–WAM 통합을 입증한 결과는 아니다.** R7과 R8은 전달량·도구 규칙이 달라 직접적인 인과 비교로 쓰지 않는다.

격리 서버의 실제 L1을 seed와 대조했다. 새 catalog에서는 version 번호가 다시 1부터 시작하므로 기존 서버와 opaque version_id가 같더라도 본문이 같다고 보지 않는다. Calendar 변경을 최종 기본 seed에 남겼으며, 최종 격리 catalog의 실제 L1과 고정 버전 L2도 source와 일치했다. 기존 공유 서버는 변경하지 않았다. 기존 ID를 건너뛰는 기본 seed의 명시적 갱신 경로는 #127로 추적한다. 시험 후 실제 앱의 자동 기억 두 스위치는 원래 true/true로 복원하고 파일에서도 확인했다.

로컬 증거: `target/e2e-logs/bench/productivity-live126-r8/`의 `calendar-{T,M}-result.json`, 입력 검증, `calendar-matched-wrapper-proof.json`, `calendar-{T,M}-independent-popups.json`, `calendar-{T,M}-cleanup.json`, `calendar-comparison.json`, `calendar-retrieval.json`, `seed-source-proof.json`, `final-seed-source-proof.json`, `settings-restored.json`, `prefill-probe.json`. 계정 원본 화면과 전체 실행 로그는 공개 저장소에 넣지 않는다.

R7은 앱 기능 확인 기록이며 속도 비교 근거에서 제외했다.

## R7 — 0.1.60 기능 수용 확인 (속도 비교에서 제외)

R7 실행은 반복 일정 생성·독립 재확인과 0.1.60 포커스 수정 후의 기능 수용을 확인하는 용도였다. 조건별 1회, 고정 순서·공유 로그인 상태였고 T의 브라우저 키 입력 묶음은 요청 허용 목록에 없었으며, 양쪽 시작 프롬프트도 달랐다. 따라서 실행 시간과 호출 수는 공개 벤치마크 근거로 쓰지 않는다. R8의 조건별 관찰만 위의 최신 Calendar 비교에 표시한다.

서명된 0.1.60 앱과 MCP를 교체한 뒤 실제 채팅 입력창에서 반복 메뉴를 열고 닫는 동작을 확인했다. 기능 검증에서는 각 조건이 만든 QA 일정의 전체 회차와 한 회차 변경을 별도 탭에서 다시 열어 확인했다. 일정은 자체 테스트 건만 정리했고 기존 일정은 보존했다. 설정 복원과 원본 화면은 로컬 기록에만 둔다.

## R6 — 0.1.59 실제 앱에서 남은 포커스 문제 확인

Codex 도구 허용 목록 수정 `3ed8215`를 포함한 0.1.59를 세 운영체제에 배포하고 Mac의 GUI와 MCP를 함께 교체했다. 실제 앱 채팅에서 확인창 inspect/dismiss와 다운로드 조회를 호출해 검증했다(39.670초, 외부 도구 경계 10회, 52바이트 파일 원문 일치).

이번 대조군은 실제 앱 UI와 실제 XDG 설정 경로에서 자동 기억 두 스위치 꺼짐을 확인했다. 채팅 입력창 copyback 및 실행기 user 기록의 전체 요청 1,176자가 원문과 일치했고, 자동 Workspace history와 Browser know-how 주입이 없었다.

|---|---|---:|---:|---|

T의 명시적 memory 호출 0, 탐지한 DOM 변경 패턴 0이다. 독립 탭에서 정확한 QA 제목을 새로 검색해 결과 0건을 확인했다. 유효한 입력을 받은 단일 대조군 기록이며, 짝이 되는 M 실행이나 메모리 개선 효과는 아직 없다. 도구 설명을 반환한 catalog-only 출력은 오류 집계에서 제외했다.

별도 새 빈 편집기에서 반복 컨트롤이 활성(aria-disabled=false)임을 확인했다. CEF 자동 클릭은 성공 응답 뒤에도 메뉴가 닫혀 있었지만, 같은 좌표를 네이티브 OS로 클릭하면 열렸다. 페이지의 빈 곳에 네이티브 포커스를 준 뒤에는 같은 CEF 클릭도 동작했다. 다시 채팅창을 누르면 document.hasFocus=false이고 CEF 클릭 뒤에도 false 및 메뉴 닫힘 상태가 유지됐다. 이 동작은 별도 자동 검사에서 실제로 실패했다.

계정 없는 격리 CEF에서도 trusted click 1회 후 앱의 폴링이 페이지 포커스를 회수해 메뉴가 닫히는 현상을 재현했다. CEF 마우스 경로가 앱의 페이지 포커스 의도를 갱신하지 않아 GPUI 회수 가드가 개입하는 코드 경로를 확인했고, #125에서 수정 `30bc7b3`에서 페이지 포커스 의도와 네이티브 responder를 함께 맞추되, 이미 포커스를 소유한 렌더러는 재지정하지 않도록 했다. CEF 208개·채팅 포커스 1개와 격리 실제 CEF 5개 검사가 통과했고 전후 이미지를 검사했다. 고정 소스 `3fe67c6`으로 0.1.60을 준비 중이며 실제 계정 전체 성공은 아직 확인하지 않았다. 좌표·스냅샷 참조 문제나 메모리 부족으로 단정하지 않는다.

R6 로컬 증거: `target/e2e-logs/bench/productivity-live103-r6/`의 `calendar-T-result.json`, 입력 검증 JSON, `calendar-native-focus-red.json`. 계정 없는 재현은 Arise 저장소의 `target/e2e-logs/native-focus125-before/`에 있다. 원본 계정 화면은 공개 저장소에 포함하지 않는다.

## R3 환경과 비교 조건

- 설치본: Arise 0.1.57, macOS arm64. 앱과 bundled MCP에 `06d991a`의 클릭 안정화 코드가 포함됨을 확인했다.
- 실행 모델: Codex `gpt-6-luna`, effort `max`; Arise 앱의 새 대화에서 실행한다.
- T: 자동 personal/WAM recall을 끄고 명시적 memory 도구도 금지한다. 실제 도구 기록으로 위반 여부를 확인한다.
- M: 같은 조건의 새 대화에 실제 WAM recall 및 version-pinned L2 expand 결과를 명시적으로 제공한다. 자동 Arise–WAM 통합 검증은 아니다.
- 조건당 1회, T→M 고정 순서의 파일럿이다. 반복·무작위·격리 계정 벤치마크로 해석하지 않는다.
- 조건별 제한은 15분이다. 도구 호출 완료는 저장 성공이 아니며, 독립된 화면 재확인이 성공 기준이다.

## 고정 작업과 성공 기준

1. 정확한 QA 제목으로 2026-11-02 09:00–09:30, `America/Los_Angeles` 일정 생성.
2. 매주 월요일만 반복하고 총 3회, 11월 2·9·16일에 종료.
3. 11월 9일 한 건만 10:00–10:30으로 이동. 2일과 16일은 그대로 유지.
4. 세 일정을 저장 후 다시 열어 날짜·시간·시간대·변경 범위를 확인하고, 11월 23일에는 없음을 확인.
5. 검증 후 실행이 만든 QA 일정만 정리. 기존 일정·전역 시간대는 변경하지 않고 게스트를 추가하지 않는다.

## T 실행의 독립 확인

T는 11:58:12 UTC에 시작했고, 15분 한도 뒤 운영자가 12:13:32 UTC에 중단했다. 실제 관찰 시간은 약 920초로, 중단 조작 지연 약 20초가 포함된다. 성공 완료 시간으로 사용하지 않는다. 위 호출 수는 실제 외부 도구 경계 수이며, 배치 안의 여러 브라우저 동작은 한 번으로 센다. 준비·독립 확인·정리 호출은 제외한다. 토큰 수는 호스트에서 유효하게 수집하지 못해 보고하지 않는다.

실행 후 별도 탭의 정확한 QA 제목 검색에서 세 일정만 찾았고 세 팝업을 각각 다시 열었다. 모두 서울 표시 시간 11월 3·10·17일 02:00–02:30, 요약은 매주 월요일 3회·로스앤젤레스였다. 이는 LA 11월 2·9·16일 09:00–09:30에 해당하며, 요청한 11월 9일 변경은 저장되지 않았다. 네 번째 일정은 검색되지 않았다.

QA 시리즈만 ‘모든 일정’ 범위로 삭제한 뒤 새 검색에서 0건을 확인했다. T가 연 12개 작업 탭도 닫고 실제 제거를 확인했으며, 기존 사용자 탭과 로그인 준비 탭은 유지했다. 실행 중 데스크톱에 leave/reload JavaScript Confirm이 보였고 renderer timeout·검은 화면이 발생했으나, 대화상자가 모든 오류의 단일 원인이라는 결론은 내리지 않았다.

## M 실행의 독립 확인과 해석

M은 12:19:20.886–12:28:02.130 UTC, 약 521초(8분 41초)에 실패를 명시하고 종료했다. T와 같은 모델·effort 및 자동 기억 꺼짐 상태의 새 대화였으며, 버전을 지정해 실제 조회한 힌트 세 개를 프롬프트로 제공했다. 다른 메모리 도구 호출이나 탐지한 DOM 변경 패턴은 없었다.

## 후속 원인 재현과 코드 수정

로그인 질문이 시간 초과된 뒤에도 독립적인 원인 조사를 이어갔다. 로그인 데이터를 쓰지 않는 동일 재현 페이지에서 설치된 0.1.57 GUI의 격리 복사본은 JavaScript 확인창을 연 뒤 페이지 읽기가 **6.004초 후 renderer timeout**으로 실패했다. 수정본은 대기 중인 확인창을 즉시 보고하고 명시적 응답 후 계속 진행했다. 따라서 네이티브 확인창 처리 누락이 이런 시간 초과를 만드는 한 원인임은 확인했으나, 기존 캘린더의 모든 실패를 같은 원인으로 단정하지 않는다.

Arise 소스 커밋: **`f525a6d`** (`fix/js-dialog-control-20261030`). 확인창을 조회하고 현재 ID를 명시해 수락·취소하는 `browser_dialog` 경로를 앱과 MCP에 추가했다. 오래된 ID·다른 리스의 응답, 사용자 인계·만료 후 대기 중이던 승인은 거부하며, 취소 시 초안을 보존한다. `wait_for`도 대기 중인 확인창을 일반 로딩으로 반복 폴링하지 않는다.

검증은 focused 테스트 **388개**, 격리된 실제 CEF의 **12개 시나리오**에서 통과했다. 확인/취소·한글 prompt·alert·지연 승인 뒤 후속 확인창·리스 종료·beforeunload 초안 보존·명시적 화면 이동을 검증하고 최종 PNG도 검사했다. 소스는 별도 worktree에 커밋했으며 원래 배포 브랜치는 정리했다.

**R3 종료 당시에는 설치된 앱과 MCP를 교체하지 않았다.** 이후 0.1.58로 함께 배포·설치했다. 위 R3 실패 결과와 메모리 효과 미검증 상태는 그대로 유지한다. 합성 증거는 Arise 저장소의 `target/e2e-logs/js-dialog27-before/`, `js-dialog27/`에 있으며 실제 계정 자료를 포함하지 않는다.
