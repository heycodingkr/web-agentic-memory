# 실사이트 벤치마크 설계 (L6 확장)

목적: 같은 에이전트가 **메모리 없음 / 수동 recall / 자동 주입**에서 실제 웹 업무를 얼마나 빨리, 적은 턴으로, 적은 오류로 끝내는지 반복 측정한다.
이 문서는 기존 에디터 파일럿(Medium, Naver, fixture)에 **Google Slides 이미지 생성**과 **Google Flow 영상 제작**을 추가하는 사용자 작업 벤치 설계다. URL+키워드 검색 알고리즘, DB/API latency, 구조화 데이터 및 sink 검증은 [`retrieval-benchmark.md`](retrieval-benchmark.md)를 따른다.

상태: 설계 초안. 두 Google 서비스의 실제 화면 구조와 기능 경로는 **탐색 단계(Phase 0)에서 직접 확인한 뒤** 태스크를 확정한다. 이 문서의 UI 경로 서술은 가정이 아니라 "확인할 항목"이다.

## 1. 벤치 스위트 구성

| 스위트 | 사이트/대상 | 성격 | 위험도 |
|---|---|---|---|
| BM-ED | Medium, Naver Blog (기존 파일럿) | 텍스트 에디터, 초안 저장 | 낮음 (발행 금지) |
| BM-FX | 로컬 fixture 에디터 (리치, iframe, 팝업, 화면 밖 Save) | 통제된 기준선 | 없음 |
| BM-SL | Google Slides: AI 이미지 생성 | 로그인 필요, 생성 기능 사용 | 중간 (계정, 쿼터) |
| BM-FL | Google Flow: 영상 제작 | 로그인 필요, 장시간 생성, 크레딧/쿼터 소모 | 높음 (비용, 쿼터, 약관) |

원칙: **통제 가능한 것(BM-FX)이 기준선**이고, 실사이트(BM-ED/SL/FL)는 "관찰"로 보고한다. 실사이트는 상태가 변하므로 통제된 A/B가 아니다.

## 2. 안전과 운영 규칙 (필수)

1. **전용 테스트 계정만 사용**한다. 개인/업무 주 계정, 실제 프로필, 실제 결제 수단이 연결된 계정은 쓰지 않는다.
2. 자동화 사용이 해당 서비스 약관에 허용되는지 **실행 전에 확인**하고 결과를 기록한다. 불명확하면 실행하지 않고 수동 관찰만 한다.
3. 생성 프롬프트는 **고정된 무해한 문구**만 쓴다 (사람 얼굴, 실존 인물, 상표, 민감 주제 제외). 프롬프트 원문은 공개 메모리에 들어가지 않는다.
4. 공유, 게시, 발행, 외부 전송, 결제, 플랜 변경은 **금지**. 하네스가 해당 버튼/URL 이동을 차단하거나 즉시 실패 처리한다.
5. 로그인, 2단계 인증, CAPTCHA, 본인 확인이 나오면 **중단하고 `invalid`로 기록**한다. 우회를 시도하지 않는다.
6. 쿼터/크레딧 상한(아래 7절)을 넘으면 그날 실행을 중단한다. 소진 시 `invalid-quota`로 기록한다.
7. 실행이 만든 결과물(슬라이드, Flow 프로젝트, 다운로드 파일)은 **실행 후 정리**한다. 정리 대상은 하네스가 만든 것뿐이다.
8. 프로필은 사용자의 실제 프로필이 아니라 **일회용 복사본**이다 (기존 방식). 테스트 계정 로그인 상태만 시드한다.
9. 메모리에 들어가는 것은 **UI 조작 절차의 관측 카테고리**뿐이다. 프롬프트, 생성물, 계정 정보, 프로젝트 이름은 포함하지 않는다 (`memory-gatekeeper.md`와 `SEC-A`가 적용된다).

## 3. 측정 조건

| 조건 | 설명 |
|---|---|
| T (tools-only) | 메모리 서버 미연결, 빈 개인 메모리 |
| M (manual recall) | 메모리 서버 연결, 에이전트가 필요 시 직접 `recall` 호출 |
| I (injected) | 호스트가 자동 주입 (Arise) |

공통: 같은 모델, 같은 effort, 같은 프롬프트, 같은 도구 버전, **새 격리 상태**. 조건별 **최소 3회** (가능하면 5회), 조건 순서는 **교차/무작위** (T→M→I 고정 순서 금지: 계정 상태/쿼터/캐시가 뒤 조건에 유리/불리하게 작용).

### 학습 실행과 측정 실행 분리 (과적합 방지)

- **Phase 0 (탐색)**: 사람 또는 에이전트가 기능 경로를 처음 푼다. 이 기록에서 메모리 후보를 만든다. 이 실행은 측정에 포함하지 않는다.
- **Phase 1 (측정)**: 메모리를 게시된 상태(게이트키퍼 통과분)로 두고 T/M/I를 측정한다.
- **Held-out 태스크**: 메모리 작성에 쓰지 않은 **다른 프롬프트/다른 세부 작업**을 같은 사이트에서 추가 측정해, 메모리가 한 문장 프롬프트에만 맞춰진 게 아닌지 본다.

## 4. 지표

| 지표 | 정의 | 비고 |
|---|---|---|
| 성공 | 독립 oracle로 판정 (5절) | 에이전트 주장은 증거 아님 |
| 에이전트 활동 시간 | 첫 도구 호출부터 생성 요청 **제출**까지 | 메모리가 줄이는 부분 |
| 대기 시간 | 제출 후 서버 생성 완료까지 | **메모리로 줄지 않음**, 분리 보고 |
| 총 시간 | 위 둘의 합 | 영상 생성은 대기가 지배적 |
| 제출까지 도구 호출 수 | 외부 round-trip 수 (`browser_script` 배치는 1콜) | 핵심 지표 |
| 총 턴 수 | 모델 턴 수 | 가능하면 기록 |
| 오류 수 | 도구 오류, 잘못된 클릭, 되돌림 | 종류별 분류 |
| 탐색 낭비 | 목표와 무관한 메뉴/페이지 방문 횟수 | 트레이스에서 사람이 라벨링 또는 규칙 |
| 토큰 사용량 | 입력/출력 (가능한 경우) | 힌트 주입 비용 포함 |
| 크레딧/쿼터 소모 | 서비스가 표시하는 소모량 | 비용 측면 |
| 재시도 횟수 | 생성 실패 후 재요청 | 서비스 불안정과 구분 |

**핵심 보고 방식**: 영상/이미지 생성은 서버 렌더링 시간이 길고 변동이 크다. 그래서 헤드라인 지표는 **"생성 요청을 제출하기까지의 시간과 도구 호출 수"** 로 하고, 총 시간은 참고로 함께 적는다. 대기 시간을 메모리 효과로 오해하게 보고하지 않는다.

## 5. 태스크 정의와 독립 oracle

### BM-SL — Google Slides AI 이미지 생성

| ID | 태스크 (프롬프트는 고정 문구) | 성공 oracle |
|---|---|---|
| BM-SL-01 | 새 프레젠테이션(테스트 계정)에서 한 슬라이드에 지정한 무해한 프롬프트로 AI 이미지를 생성해 삽입 | 프레젠테이션을 **읽기 전용 API 또는 내보내기**로 확인: 대상 슬라이드에 이미지 요소 1개 이상, 크기/URL 유효 |
| BM-SL-02 | 기존 슬라이드의 이미지를 다른 프롬프트로 생성한 이미지로 교체 | 이미지 요소가 교체됨 (요소 ID 또는 콘텐츠 해시 변경), 이전 이미지 제거 |
| BM-SL-03 (held-out) | 두 슬라이드에 각각 다른 이미지 생성, 위치/크기 지정 | 요소 수와 대략적 위치/크기 일치 |

- Phase 0에서 **어떤 기능 경로로 이미지를 생성하는지**(메뉴 위치, 패널, 입력 필드, 생성 버튼, 삽입 버튼)를 확인해 기록한다. 기능이 계정/플랜/지역에 따라 없으면 `unavailable`로 기록하고 이 스위트를 건너뛴다.
- 이 세션에는 Google Slides 읽기용 MCP 도구가 있으나, 사용하려면 별도 인증이 필요하다. oracle용 읽기 도구는 **에이전트와 분리된 경로**로 실행한다 (에이전트가 oracle 결과를 보지 못하게).
- 생성 이미지의 **미적 품질은 자동 판정하지 않는다.** 필요하면 별도의 블라인드 사람 평가를 부가 지표로만 둔다.

### BM-FL — Google Flow 영상 제작

| ID | 태스크 | 성공 oracle |
|---|---|---|
| BM-FL-01 | 새 프로젝트에서 고정 프롬프트로 짧은 영상 1개 생성 | 프로젝트 화면에 완료된 클립 1개, 다운로드 파일이 있다면 `ffprobe`로 길이 > 0, 해상도/코덱 확인 |
| BM-FL-02 | 이미지를 시작 프레임으로 영상 생성 (기능이 있으면) | 완료된 클립 1개, 입력 이미지 사용 표시 |
| BM-FL-03 (held-out) | 같은 프로젝트에서 두 번째 클립 추가 | 클립 2개 |

- **기능 경로, 입력 방식, 소모되는 크레딧, 생성 소요 시간은 Phase 0에서 실측**해 기록한다. 다운로드가 약관/플랜상 불가능하면 oracle을 "프로젝트 UI의 완료 상태 + 클립 메타데이터"로 대체하고 그 한계를 명시한다.
- 영상 생성은 **서버 대기가 수 분 단위일 수 있다.** 실행 타임아웃, 폴링 주기, "생성 중"과 "실패"의 구분 규칙을 하네스에 명시한다 (조용한 상태를 완료로 판정 금지).
- 한 회당 크레딧 소모가 크면 반복 횟수를 **3회**로 줄이고, 줄였다는 사실과 이유를 결과에 적는다 (조용한 축소 금지).

### BM-ED / BM-FX (기존)

기존 파일럿 태스크를 그대로 재사용하되, 반복 횟수와 조건 순서 교차를 새 프로토콜로 맞춘다. 상세는 `functional-tests.md`의 PERF-01~06.

## 6. 실행 하네스

현재 공용 실행기는 [tests/bench](../../tests/bench/README.md)에 있다. 계획을 실행 전에 저장하고 run별 격리 환경·가드 callback·트레이스·무효 분류·통계를 연결한다. CLI replay는 저장된 정규화 트레이스와 독립 oracle 결과를 재처리하며 성능 주장 등급을 C로 제한한다. 실제 호스트의 trace normalization과 browser interception은 별도 adapter 작업이다. [사전 등록 템플릿](prereg/_template.md)을 채우고 실행 전에 커밋한다.

- 기존 `probe_agent_memory_live.py`, `probe_agent_site_live.py`를 확장한다 (실제 채팅 경로 → 트레이스 JSONL → 명시적 Done/Failed).
- 각 run은 별도 앱 복사, XDG 설정, 세션, 브라우저 캐시, TMPDIR(짧게, 예: `/tmp/wam-*`), 로컬 fixture/oracle을 갖고, 종료 시 **자기 프로세스 그룹만** 정리한다.
- 트레이스에 `submit` 이벤트(생성 요청 제출)를 기록해 활동/대기 시간을 자동 분리한다.
- 비가역/비용 행동 가드: 허용 URL/버튼 목록 밖의 동작(공유, 게시, 결제)은 하네스가 차단하고 `blocked-action`으로 기록한다.
- 결과는 `target/e2e-logs/bench/<suite>/<run-id>/`에 `cases.jsonl`, `trace.jsonl`, `summary.md`, 스크린샷으로 남긴다 (`docs/test/README.md` 5절 증거 규약).

## 7. 비용/쿼터 예산 (실측 후 확정)

| 항목 | 규칙 |
|---|---|
| 일일 상한 | 서비스별 일일 생성 횟수/크레딧 상한을 Phase 0에서 측정해 그 50% 이하로 설정 |
| 총 예산 | BM-SL, BM-FL 각각 최대 실행 수를 사전에 확정해 문서에 기록 |
| 소진 시 | 중단, `invalid-quota`, 다음 날 재개 |
| 사전 예측 | (조건 3 × 반복 3 × 태스크 수)가 예산을 넘으면 태스크 또는 반복을 줄이고 기록 |

## 8. 무효(invalid) 분류

실패(메모리가 해결해야 할 문제)와 무효(측정 불가)를 구분한다. 무효는 통계에서 제외하고 사유와 함께 보고한다.

| 분류 | 예 |
|---|---|
| `invalid-auth` | 로그인 만료, 2FA, CAPTCHA |
| `invalid-quota` | 쿼터/크레딧 소진, 속도 제한 |
| `invalid-service` | 서비스 5xx, 생성 서버 장애 (메모리로 해결 불가) |
| `invalid-ui-drift` | 실행 중 UI가 바뀌어 태스크 경로 소멸 → 메모리 재작성 필요 (G6 근거) |
| `invalid-env` | 하네스/환경 문제 (잘못된 MCP 설정 디렉터리 등) |
| `unavailable` | 계정/지역/플랜에 기능 없음 |

## 9. 결과 보고 형식

```
스위트 | 태스크 | 조건 | n | 성공률 | 제출까지 시간 (평균 ± 표준편차) | 제출까지 도구 호출 (평균 ± sd) | 오류 | 대기 시간 | 크레딧 | 무효 n
```

규칙:
- 평균과 편차, n을 함께 적는다. n < 3이면 "예비 관찰"이라고 명시한다.
- 같은 모델/effort/도구 버전끼리만 비교한다.
- **개선이 없거나 악화된 경우도 그대로 보고**한다 (예: 자동 주입이 수동 recall보다 느린 경우).
- 호스트별(Arise 자체 메모리 자동 주입, Claude Code/Codex + WAM 수동 recall)로 분리한다.
- 헤드라인 수치는 README에 옮길 때 **어느 조건/n에서 나온 값인지**를 같이 적는다.

## 10. 메모리 입장에서 기대할 수 있는 것과 없는 것

| 메모리가 도울 가능성이 큰 것 | 메모리로 해결되지 않는 것 |
|---|---|
| 기능 경로 발견 (어떤 메뉴/패널을 열어야 하는지) | 생성 서버의 대기 시간 |
| 입력 필드/버튼 위치, 포커스 요령 | 쿼터/크레딧 한도, 서비스 장애 |
| 생성 완료 판별 방법 (어느 상태가 완료인지) | 생성 품질 |
| 흔한 실수 회피 (모달, 팝업, 권한 안내) | 로그인, 2FA, CAPTCHA |
| 불필요한 탐색과 재시도 감소 | 계정/플랜에 기능이 없는 경우 |

이 표를 README의 수치 해석에도 그대로 쓴다. 대기 시간이 큰 작업에서 총 시간 개선폭이 작게 나오는 것은 예상된 결과이며, 가치는 **제출까지의 시간, 호출 수, 오류 수**에서 본다.
