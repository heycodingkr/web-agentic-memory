# Preregistration: 2026-11-01 / Notion R9 development comparison

Status: frozen before measured runs. The separate checkout commit is recorded in plan.json. This is an uncontrolled development comparison (grade C), using an explicitly supplied candidate L1, not automatic WAM integration.

- Hypothesis: a single task-specific Notion hint reduces redundant property/page/view navigation while preserving the requested result.
- Host: installed Codex CLI 0.166.0, gpt-6-luna, max effort; installed Arise browser MCP. One fresh ephemeral Codex history/config and working directory per run. Only the existing Codex login credential and the explicitly selected signed-in browser connection are reused; no user settings or conversation history are copied.
- Task: create a new private QA database with Name, Status and Due, Alpha QA (In progress, 2026-11-10) and Beta QA (Done, 2026-11-17), All QA tasks sorted by Due ascending, and Active QA tasks grouped by Status with completed tasks excluded. Reload and verify once. No page body content, sharing, messages, invitations, publication or payments.
- Conditions: T has the task only. M adds one frozen candidate L1; no L2 and no memory tools. Each run has a unique QA title but the same task and tool rules.
- Candidate L1: Notion task databases: choose a database, not a simple table. Reuse an existing Status property; add Due as Date only if missing. Set dates and statuses in table cells; open an item body only when requested. Add the Board as another view of the same database. A Complete status-group filter includes Done. If view tabs or cells are clipped, collapse the sidebar once. Check each requested view after the final reload.
- Fixed crossover order: b1-M, b1-T, b2-T, b2-M, b3-M, b3-T; three runs per condition. Order alternates but is not randomized.
- Primary metrics: wall time from first MCP tool-call event to model completion; number of direct MCP calls through completion. Transport initialization before the first call and independent verification/cleanup are excluded. Never compare these values directly to R7/R8's different host/protocol.
- Oracle: a separate persistent read-only observer opens the exact QA URL in a fresh tab, checks the exact title, both rows and dates/statuses in the table, Due ascending sort, Status grouping, Alpha-only board and private sharing. Captured UI text and screenshots are local evidence. A model completion or its own claimed success cannot pass the oracle.
- Cleanup: the observer may move only an exact matching new QA page and its child rows to Trash; never restore or permanently delete anything. Cleanup failure is reported separately.
- Bound: 900 seconds and at most 230 MCP calls per run; at most six measured attempts. No unplanned retries. Shell, web search, scripts, API writes, delegation and memory tools are unavailable to the model.
- Exclusions: login/quota/service/transport/harness failures are retained and labeled invalid. Abort on a transport/harness invalid run rather than publishing partial performance claims. Ordinary UI/task failures remain failures. More than 20% invalid invalidates the suite.
- Reporting: retain every run and failed/invalid result locally. Report success counts and per-condition medians. A headline improvement requires all independent checks to pass, at least 20% median reduction in time and calls, and a positive 95% paired bootstrap interval (10,000 samples). Otherwise mark the candidate unproven and do not promote it to the default seed. No general or causal performance claim is allowed from this development comparison.
- Evidence: target/e2e-logs/bench/notion-r9-20261101/. Candidate text/hash, order, inputs, raw tool boundaries, independent checks, UI captures and cleanup are bound to that evidence root. Account URLs, raw traces and credentials are not public artifacts.
- Limitation: one workflow and a shared logged-in browser/profile/cache, with no held-out workflow or fresh account per run. Other sessions may interrupt the foreground browser; record such an interruption as an environment failure.
